Docker Infrastructure

All files — docker-compose.yml, vault.hcl, TLS certs, data, and logs — live under:
C:\Users\mail2\source\repos\IntegratedAPP\IntegratedAPI\vault-enterprise\
Run all commands from this directory or use the full paths shown below.
Critical: Always override the entrypoint. The default entrypoint of the hashicorp/vault image mangles the -config flag by stripping the .hcl extension, producing "stat /vault/config/vault: no such file or directory". Always use --entrypoint sh and pass the full command via -c. The Docker Compose file below already handles this correctly.

docker-compose.yml — the preferred way to start Vault:

docker-compose.yml
services:
  vault:
    image: hashicorp/vault:latest
    container_name: vault-enterprise
    ports:
      - "8200:8200"
    volumes:
      - ./config:/vault/config
      - ./data:/vault/data
      - ./logs:/vault/logs
      - ./tls:/vault/tls:ro
    cap_add:
      - IPC_LOCK
    entrypoint: sh
    command: -c "vault server -config=/vault/config/vault.hcl"

First-Time Initialization

One-time only. Run this exactly once on a fresh data\ directory. The 5 unseal keys and root token cannot be recovered if lost. Store them in a password manager before doing anything else.
PowerShell — Initialize Vault (run once only)
docker exec `
  -e VAULT_ADDR='https://127.0.0.1:8200' `
  -e VAULT_SKIP_VERIFY='true' `
  -it vault-enterprise `
  vault operator init

Output will look like this — save all 5 keys and the root token:

Example Output
Unseal Key 1: abc123...
Unseal Key 2: def456...
Unseal Key 3: ghi789...
Unseal Key 4: jkl012...
Unseal Key 5: mno345...

Initial Root Token: hvs.XXXXXXXXXXXXXXXX
Init data is persisted to vault-enterprise\data\ via the mounted volume. It survives container removal and recreation. Never delete the data\ folder.

After init, immediately proceed to the Unseal Ceremony to bring Vault online.

Unseal Ceremony

Frequency: Required every time the container starts or restarts. Vault always boots sealed — this is by design for security. Your data is safe in data\; you just need to supply 3 of your 5 unseal keys each time.

Run the unseal command 3 times, entering a different key each time when prompted:

PowerShell — Unseal (run 3 times with 3 different keys)
docker exec `
  -e VAULT_ADDR='https://127.0.0.1:8200' `
  -e VAULT_SKIP_VERIFY='true' `
  -it vault-enterprise `
  vault operator unseal

After the 3rd key, Vault reports Sealed: false. Then log in to establish your session token inside the container:

PowerShell — Login with Root Token
docker exec `
  -e VAULT_ADDR='https://127.0.0.1:8200' `
  -e VAULT_SKIP_VERIFY='true' `
  -it vault-enterprise `
  vault login
Token persistence caveat: vault login stores the token inside the running container's filesystem. Subsequent docker exec calls on the same container share this token. However, if you remove and recreate the container, you must run vault login again after unsealing. Alternatively, pass -e VAULT_TOKEN=hvs.XXXX explicitly on every admin docker exec to avoid relying on the stored token.
Full restart workflow: docker compose up -d → Unseal ×3 → Login. That's all you need each time Docker Desktop or your machine restarts.

Policies & Secrets

Do not use PowerShell echo to pipe policy HCL. PowerShell mangles the double quotes, producing a "failed to parse policy: comment not terminated" error. Use the file-based method below instead, which works reliably from PowerShell.

Step 1 — Enable the KV-V2 secrets engine:

PowerShell — Enable KV-V2
docker exec `
  -e VAULT_ADDR=https://127.0.0.1:8200 `
  -e VAULT_SKIP_VERIFY=true `
  vault-enterprise `
  vault secrets enable -path=tenants kv-v2

Step 2 — Create the policy using a file (avoids all quoting issues). Since config\ is already mounted inside the container, save the policy file there:

PowerShell — Write & Apply Policy
# Write policy HCL to the config folder — mounted inside container at /vault/config
Set-Content `
  -Path "C:\Users\mail2\source\repos\IntegratedAPP\IntegratedAPI\vault-enterprise\config\policy.hcl" `
  -Value 'path "tenants/data/*" { capabilities = ["read"] }'

# Apply it — the file is visible inside the container at /vault/config/policy.hcl
docker exec `
  -e VAULT_ADDR=https://127.0.0.1:8200 `
  -e VAULT_SKIP_VERIFY=true `
  -it vault-enterprise `
  vault policy write tenant-reader /vault/config/policy.hcl

Step 3 — Store a secret:

PowerShell — Add a Secret
docker exec `
  -e VAULT_ADDR=https://127.0.0.1:8200 `
  -e VAULT_SKIP_VERIFY=true `
  vault-enterprise `
  vault kv put tenants/WIPRO connectionString="Server=SQL_WIPRO;Database=mydb;User Id=sa;Password=secret;"
Secrets are stored at path tenants/data/<TENANT_NAME> in KV-V2. Add more tenants by repeating the vault kv put tenants/<NAME> command with different tenant names.

AppRole Authentication

PowerShell — Enable AppRole & Create Role
# Enable AppRole auth method
docker exec -e VAULT_ADDR=https://127.0.0.1:8200 -e VAULT_SKIP_VERIFY=true vault-enterprise vault auth enable approle

# Create a role and bind the tenant-reader policy
docker exec -e VAULT_ADDR=https://127.0.0.1:8200 -e VAULT_SKIP_VERIFY=true vault-enterprise vault write auth/approle/role/dotnet-api-role token_policies="tenant-reader"
PowerShell — Retrieve Credentials for .NET
# Get the Role ID
docker exec -e VAULT_ADDR=https://127.0.0.1:8200 -e VAULT_SKIP_VERIFY=true vault-enterprise vault read auth/approle/role/dotnet-api-role/role-id

# Generate a Secret ID
docker exec -e VAULT_ADDR=https://127.0.0.1:8200 -e VAULT_SKIP_VERIFY=true vault-enterprise vault write -f auth/approle/role/dotnet-api-role/secret-id
Copy the Role ID and Secret ID from the output into your .NET app configuration. These are the only credentials your application needs to authenticate with Vault at runtime.

Vault UI Management

The GUI is available at https://127.0.0.1:8200. Your browser will show a TLS warning because the cert is self-signed — click Advanced → Proceed. Log in with your Root Token.

The UI is only accessible after Vault has been unsealed. If you see a connection error or blank page, complete the unseal ceremony first.
UI ACTION Managing Secrets: Navigate to Secrets → tenants. Click an existing secret to add a new version, or Create Secret to add a new tenant.
UI ACTION Modifying Policies: Navigate to Policies. Edit the tenant-reader HCL directly in the browser to add or change path permissions.

.NET 9 Integration

Program.cs (VaultSharp v1.17.5.1)
var vaultClientSettings = new VaultClientSettings(uri, authMethod)
{
    PostProcessHttpClientHandlerAction = handler =>
    {
        if (handler is HttpClientHandler httpClientHandler)
        {
            httpClientHandler.ServerCertificateCustomValidationCallback =
                (message, cert, chain, sslPolicyErrors) => true;
        }
    }
};
builder.Services.AddSingleton<IVaultClient>(new VaultClient(vaultClientSettings));
The ServerCertificateCustomValidationCallback bypasses TLS validation for the self-signed cert. For production, replace this with a CA-signed certificate or proper certificate pinning.

Troubleshooting

  • "stat /vault/config/vault: no such file or directory"
    The default image entrypoint strips the .hcl extension. Always use --entrypoint sh with -c "vault server -config=/vault/config/vault.hcl". The provided docker-compose.yml already handles this correctly.
  • "Error opening policy file: no such file or directory"
    The policy file was saved to the wrong location. It must be saved to C:\Users\mail2\source\repos\IntegratedAPP\IntegratedAPI\vault-enterprise\config\policy.hcl — not to C:\vault-enterprise\ or any other path. Use the exact Set-Content -Path command in Section 4.
  • "listen tcp4 0.0.0.0:8200: bind: address already in use"
    Run netstat -ano | findstr :8200. If state is TIME_WAIT with PID 0, there is no active process — wait ~60 seconds for the OS to release the socket, then retry. Also run docker rm -f vault-enterprise to clear any stopped container with that name before starting a new one.
  • "Conflict. The container name '/vault-enterprise' is already in use"
    Run docker rm -f vault-enterprise first, then re-run your start command. With Docker Compose, use docker compose down followed by docker compose up -d.
  • "permission denied" (403) on vault commands
    The token from a previous vault login does not carry over after the container is removed and recreated. Run vault login again after unsealing, or pass -e VAULT_TOKEN=hvs.XXXX explicitly on every admin docker exec command.
  • "failed to parse policy: comment not terminated" (400)
    Caused by PowerShell mangling double quotes in echo "..." | docker exec pipelines. Use the file-based approach in Section 4: write the policy to config\policy.hcl with Set-Content, then apply it via vault policy write tenant-reader /vault/config/policy.hcl.
  • "core: security barrier not initialized" in logs
    Normal on a fresh data\ directory. Run vault operator init as described in Section 2.
  • Vault is sealed after every restart
    By design. Run the unseal command 3 times with 3 different keys after every container start. Your secrets data is safe in vault-enterprise\data\.
  • TLS handshake error / "tls: unknown certificate" in logs
    Expected with a self-signed cert. Always include -e VAULT_SKIP_VERIFY=true in all docker exec commands. In the browser, click Advanced → Proceed. Ensure the cert was generated with -addext "subjectAltName=IP:127.0.0.1".
  • Task vs Result error in .NET controller
    Ensure you await the VaultSharp service call. Missing await returns a Task object instead of the actual result.
  • Property errors with VaultSharp
    For VaultSharp 1.17.x, use PostProcessHttpClientHandlerAction for TLS configuration. The older MyHttpClientProviderFunc property no longer exists in this version.
